## 类间公平性：从 0.25 到 1.02（2026-07-11 深夜）

把 M2 场景的真实类间比例从严重失衡（50ms 下 0.25、1ms 下 0.40）修到
1.02-1.05 的过程，三个缺陷：

1. **类归因失真**（测量面，跨周期）：megaflow 类构成比有 2 秒滞后
   （硬件计数器 1s 缓存 + 2s 滑窗），竞争期两类秒级交替占优时会把每个
   瞬时总量按时间平均错切（TCP 突发 5G/RDMA 实际 1G 的时刻被报成
   3G/3G）。修复：接收端 host 速率导出 shim，每 5ms 把 netdev rx_bytes
   经 tmfifo 推给 rx_agent（判别实验证明 RoCE 完全绕过内核 netdev 计数
   器：16.4GB 纯 RDMA 只让 netdev rx_bytes 动了 2386 字节）。这套机制
   后来被 2026-07-13 的 vport 直读方案取代（见主设计文档 §6.1），但
   "RoCE 绕过内核计数器"这个判别实验本身仍是有效证据。
2. **HAI 无视 grant 冲穿**（响应律，振荡的主引擎）：无标记 0.5 秒后
   HAI 以 16G/s 墙钟斜率冲向 tree 上限，冲穿→VQ 饱和→标记风暴→MD
   深砍→再冲，15-25 秒周期弛豫振荡。修复：AI/HAI 探测上界锚在
   `ceil_f × probe_over_grant(1.05)`——这是 AIMD 时代的"探测余量"补丁，
   已被 MIMD 的无余量硬顶 ê 结构性淘汰（见主设计文档 §12 修订一/七）。
3. **转换期压穿 + RP 死锁**：类进入/退出时标记风暴把 R 打到 pace 地板，
   RP 因"只在喂率变化时迈步"永久卡死。修复：MD 下界 R≥0.3r + RP 喂率
   交替抖动。

验收（1ms/1:1/三轮）：竞争段 wire 比例 1.03-1.05，秒级振荡 stdev
0.01-0.15（修前 1.6-1.9），借用 1s 内回满，回收 <20 周期。口径选择：
以**线上字节**为主（VM 额度买的就是链路字节，调度器输入天然是 wire
口径），goodput 辅助报告（两口径给出同样结论）。

## 控制周期 1ms 化：延迟预算实测（2026-07-11）

按大小排序的延迟预算：① RDMA 执行——PCC mailbox 单次调用阻塞 **13.3ms**
（固件层往返，改不动，是最大瓶颈）；② TCP 执行——tmfifo 一跳 1-4ms
（后取消这一跳，TCP 响应律搬到 host shim 本地执行）；③ 接收端
measurement——megaflow dump 0.9-1.3ms/tick（构成比只有 1 秒新鲜度，
不需要每 tick 拉，快慢环分离解决）；④ vport 计数器新鲜度——p50 0.87ms、
p99 3.7ms（**物理下限**，决定了 1ms 量级可行、0.1ms 不可行）；⑤ Python
全流程开销——瘦身后 131µs/tick（不需要 C 重写，有 8 倍余量）；⑥ 遥测
线路——SF 网往返 0.1ms（达标）。

## 控制周期 1ms 化：调参全过程（2026-07-11）

**已完成**：延迟预算实测（上一节）；快慢环分离（快环 1ms 只读 vport+
水填充+发遥测，慢环 200ms 才做 megaflow dump）；遥测改二进制定长；
RDMA 预算合并写解耦（控制律 1ms 跑、mailbox 按 13ms 合并推）；参数按
周期时间语义自动缩放。**一个藏得很深的测量 bug**：慢环 dump 落在两次
vport 采样之间会把字节计数和时间戳解耦，导致速率虚高虚低交替（±60%
抖动）——修复是固定样本数窗口（不是时间窗）+ vport 采样固定在循环
最顶端。这个 bug 是所有后续调参的前提。

**排查出的核心矛盾链**（按时间顺序，后一条推翻/精化前一条）：
1. 最初怀疑 PCC RP 内环耦合（RP 只在喂率变化时迈步，1ms 平滑去掉了
   50ms 时依赖的抖动）——但验证 TCP 路径（走 host EDT，与 RP 无关）
   后发现同样欠利用（66-77% vs RDMA 84%），**排除 RP 耦合是主因**，
   病根在接收端标记动力学。
2. V（虚拟队列满刻度）的缩放本来是错的：V 应该是固定比特量（∫(r-e)dt
   与 tick 周期无关），原公式让 V∝period，1ms 下小了 50 倍、对测量
   尖峰敏感 50 倍。改成固定比特锚定参考周期后 TCP 从 3.97G 升到
   4.65G，但没到头——V 调大后 RDMA 又脱管到 18G（标记变迟钝）。
3. **最终主治病根：MD 剂量没按周期缩放**（β 漏在缩放清单外）。1ms 下
   每秒最多挨 1000 刀 β=0.3，剂量是 50ms 设计的 50 倍，一次 20ms 标记
   突发就把 R 从 3G 压穿到 0.05G 地板。修复：`R *= (1-β·s)**(period/ref)`。
4. **混淆因子：RP 内部状态会随实验翻腾劣化**（根因未查，需 device 码
   排查），每个实验批次之间重启 RP 才能拿到干净数据——"66-84%欠利用"
   的历史数据是 MD 剂量 bug + RP 劣化两个病根叠加的产物，不是标记动力学
   本征缺陷。

修复后：M1b 在 1ms 下稳定 5.66G，反超 50ms 基线约 10%，三轮可复现。
`rate_window_s` 定为 0.020（20ms，压紧稳态离散：p5 5.43→5.81、p95
7.35→6.11）。M2 类间竞争：借用/回收干净，但暴露一个新死锁——转换期
VQ 饱和 s=1 持续~1秒，MD 把 R 打到地板，RP 摁在 0.02G 后喂率恒定不再
迈步，预算涨到 12.6G 也没用（RDMA 饿死到 TCP 离场）。修复两条（均在
tx_agent_e.py）：MD 下界锚在实测到达率 R≥0.3·r；给 RP 喂率做交替抖动
（±max(3%, 一个单位)）保证设备码永远有变化可步进。TCP 高重传定性为
EDT 数据通路乱序（DSACK 98%，非丢包），独立于 1ms 化，未修。类归因
问题（megaflow 2s 滑窗滞后）在这里首次被识别为"下一条独立工作线"，
后来在 2026-07-13 通过 vport ib/eth 分桶直读解决。

## 压力测试战役总结（2026-07-11/12）

七个维度：D1 规模（1ms 控制面 CPU 饱和点=28 流集合，越墙温和拉长非崩）、
D2 极端比例（类权重跟随到 8:1 全部 ±10%，无悬崖）、D3 churn（让位/回满
p50 0.06-0.22s）、D4 incast（公平性完好但 root 区利用率/振荡有设计级
问题）、D7 参数边界（默认点在平坦区中央，仅两悬崖）、D8 对抗时序
（on-off 泵拿不到超过稳态份额）。D6 长稳、D5 故障均按用户指示取消。

六个修复的工程缺陷：① TCP 执行面两层覆盖缺口（EDT 只装在 vf0，跨 VF
对完全不受 pace）；② RP 跨层活锁（预算每次微变重臂 settle-hold，改为
3% 滞回）；③ 发作性标记风暴（探测锚 ceil×1.05 保证兑现率>95.2%的执行
器永久超额，改为兑现率感知的衰减余量）；④ RP 积分下挖过深（地板从
bud>>7 提到 bud>>2，唯一的 device 码改动）；⑤ 预算下降斜率限速 0.35/s
（阻尼三环极限环）；⑥ slew-off 语义 bug（decay=1.0 让预算永不下降）。
②③④中的多层补丁后来被 MIMD 的结构性硬顶淘汰（见主设计文档 §12）。

两个当时待裁决、后来都被采纳的设计发现：**V_periods 默认 2→4**（根治
incast root 区同步弛豫振荡，46G/48%/sd9.97→95G/98%/sd0.04）——这个
默认值本身在 2026-07-22 的收敛优化 campaign 里又被重新评估，发现 MIMD
的硬顶免疫已经让它可以安全改回 2（见 `results/convergence_opt_20260722/
summary.md`）；root 区利用率的律代际差（V=4 一并解决）。

参数敏感性地图（单对两类竞争，27 点扫描）：只有两个失稳悬崖，都在
"太慢/太粗"方向——`a_frac_linerate≥0.001`（默认 2 倍，比例崩到 0.50）、
`rate_window_s≥0.1`（测量窗跟不上秒级竞争）。其余（β 0.1-0.7、V
0.5-8、probe_over 1.0-1.3、probe_gain 0-100、slew 0.1-1.0）均无悬崖。

## 双类利用率欠账机理（2026-07-10，诊断完成）

双类并发合计利用率 ~85-89%（单类 97-99%）。标记本身无罪（跟踪误差仅
2-5%）；真凶是 **grant 塌陷**（demand-cap 反馈环）：TCP 的 CC 掉坑
（丢包恢复）→ r 塌 → 需求估计 D=1.15r 跟着塌 → e 瞬时跟塌（无状态需求
封顶）→ 让出的份额兄弟类也吃不下（它的 D 同样封顶在现用量附近）→
e_sum 深塌（p5 低至 2.4G）。三条候选修正（F1 需求估计滞回、F2
app-limited 解除后乘性恢复、F3 δ 分层）当时待用户裁决。这条诊断后来
被主设计文档 §9 的"三条关于利用率的实测权衡"重新审视并给出最终结论：
双类 87% 左右的利用率不是账本失误，是租户 TCP 自身丢包恢复期间发不出
流量所致，份额保底(≈F1的思路)反而会杀死借用机制，默认不采纳。

## DCQCN CNP 触发状态（2026-07-04 记录，2026-07-23 确认已解决）

`rate = min(cc_rate, level)` 的 cc_rate 项：CNP 事件降速
`cc_rate -= cc_rate>>3`、加性恢复每 epoch `+MAX_RATE>>8`。当时已验证
（冻结注入，`0xccc` 模拟持续拥塞）min() 公式、降速算术、恢复机制全部
正确；**唯一未验证的是"真实拥塞自动产生 CNP → handler 被触发"这一环**
（需要 incast 环境 + 交换机 ECN 标记）。

**后续进展**：2026-07-13/14 的 DCQCN/ECN 工作（switch ECN 配置
`ecn_incast_bzx`、cc_rate 降速改为 per-QP 归一化，见
`docs/design_and_implementation.md` 及 `dcqcn-rp-fix` memory）里，真实
CNP 已经在 incast 场景下端到端验证触发。2026-07-22 的收敛优化
campaign 进一步用设备端诊断计数器实测确认：CNP 事件确实到达算法回调
并正确匹配到 pair、乘性减确实生效（冻结加性增后 cc_rate 从满速真实
掉到约 9.6%）——但也发现一个新问题：正常运行时加性增比乘性减快太多
（单次 CNP 恢复只需~4ms），导致 cc_rate 在实践中对这层"硬件风味"
backstop 提供的保护很弱，`min(cc_rate,level)` 几乎总等于 level（详见
`cc-rate-weak-dcqcn-backstop` memory）。本文档最初记录的开放问题
（"CNP 能否到达"）已经解决；新发现的问题性质不同，不在本文档追踪范围。
